## Design principles (non-negotiable, see README § Design notes)

- **RE2 matching only** — use Go's standard `regexp`. Never shell out to or vendor a backtracking regex engine; that reintroduces ondir's catastrophic-backtracking hangs.
- **Path-segment matching, not string-prefix matching** — a pattern must match whole path segments. Never implement matching as a raw `strings.HasPrefix`.
- **Enter/leave are independent and explicit** — no automatic state snapshot/restore on leave. Don't add "smart" auto-undo; if that's ever wanted, it's a deliberate opt-in feature, not a default.
- **Trust before execution** — any new or modified config must go through an explicit `envoke allow` before its blocks run. Never auto-execute an unapproved config, even in convenience-focused code paths.
- **One binary generates all shell integration** — hook scripts for bash/zsh/fish/tcsh/powershell are generated by the binary (`envoke shell-init <shell>`), not maintained as separate hand-written files per shell.

## MVP scope order

1. ✅ Config parser + path matcher + `enter`/`leave` execution (core loop only).
2. ✅ Shell hook generation for bash and zsh (hook plumbing + match reporting).
3. ✅ `envoke allow` trust mechanism — trusted matches now actually execute via `executor.Render` + the shell's own `eval`.
4. ✅ `envoke debug <from> <to>` dry-run diagnostics — reports matches and trust status, never executes.
5. ✅ fish/tcsh/powershell shell integration — hook generation plus a shell-aware `executor.Render`.
6. ✅ CI checks via Dagger (`.dagger/` module) — `dagger check` mirrors CONTRIBUTING.md's four manual commands plus golangci-lint, and runs the shellinit end-to-end tests against a real interpreter for each of the five supported shells.
7. 🚧 Packaging (goreleaser: binaries, Homebrew tap, Scoop bucket, nfpm deb/rpm) — binaries, GitHub Release, Homebrew tap, and tag-triggered release CI all done and verified end to end against a real `v0.1.0` tag (see Status); Scoop bucket / nfpm still pending.

Don't jump ahead to later stages before earlier ones have tests passing.

## Architecture sketch

Current package layout (`internal/`, not importable outside this module — there's no stable public API to commit to yet):

- **`internal/config`** — `Parse`/`ParseFile` turn a config file into `[]Block{Type, Pattern, RawPattern, Script, Line}`. Hand-rolled line-oriented parser (see decision below), not a grammar library. Pattern compilation (`pattern.go`) expands a leading `~` and `$VAR`/`${VAR}` as literal (`regexp.QuoteMeta`'d) substitutions, then wraps the result as `^(?:...)$` before `regexp.Compile` — that anchoring is what makes matching segment-based rather than prefix-based (fixes ondir's `/home/foo` vs `/home/foobar` bug structurally, not by convention). Malformed config fails with a positioned `*ParseError{Line, Msg}`, never silently.
- **`internal/matcher`** — `Transitions(from, to)` walks both paths' ancestor chains via `filepath.Dir` to their common ancestor, returning directories left (deepest-first) and entered (shallowest-first) — this is ondir's traverse behavior: jumping straight from `/a` to `/a/x/y/z` still fires `/a/x` and `/a/x/y`'s rules. `Resolve(cfg, from, to)` runs every block's pattern against the relevant directories and returns ordered `[]Match`.
- **`internal/executor`** — two execution models sharing `matchVars` (the `ENVOKE_DIR`/`ENVOKE_TYPE`/`ENVOKE_MATCH`/`ENVOKE_MATCH_N` a matched block sees):
  - `Run(ctx, match)` execs the script via `sh -c` as a **subprocess** (`cmd.Dir` set to the matched directory, vars as env, inherited stdio). Used by `internal/envoke.Transition`; side effects like `export`/`source` don't escape this subprocess, so this path is for non-interactive/one-off execution, not the shell hook.
  - `Render(shell, leaves, enters)` builds ENVOKE_*-var-assignment-prefixed shell text for every match, in the same leave-then-enter order, meant to be `eval`'d/`source`d by the *caller's own shell*. This is what `cmd/envoke shell-hook` uses once a config is trusted — it's the only path where `export`/`source` in a script actually affects the user's interactive shell. `shell` selects a `shellProfile` (posix `export VAR=...`, fish `set -gx`, tcsh `setenv`, or PowerShell `$env:VAR = ...`) — an unrecognized name falls back to POSIX. Each profile has its own quoting function (`posixQuote`/`fishQuote`/`powershellQuote`; tcsh reuses `posixQuote`, confirmed against a real tcsh) so directory names or capture groups with spaces/`$`/backticks/embedded quotes can't break out of the generated code — regression-tested by piping `Render`'s output through a real `sh -c` (POSIX) and a real `tcsh -c`. Render can only translate the ENVOKE_* plumbing, not the matched block's own script text — a script body still needs to actually be written in the calling shell's syntax to behave when eval'd by fish/tcsh/powershell, same as it always implicitly needed to be POSIX-ish for bash/zsh.
- **`internal/envoke`** — `Transition(ctx, cfg, from, to)` is the subprocess-based core loop: resolve, then run all leaves, then all enters via `executor.Run`, stopping at the first failing block (no partial-transition unwind — see the enter/leave independence principle above). Exercised end-to-end by its own integration tests. Not used by the shell hook (see `executor.Render` above) or by `envoke debug` (which never executes anything) — it's there for non-interactive automation where "eval in the parent shell" doesn't apply.
- **`internal/config.Locate()`** — resolves the config path: `$ENVOKERC` (used verbatim, even if missing) → `~/.envokerc` if present → `$XDG_CONFIG_HOME/envoke/config` (or `~/.config/envoke/config`) if present → not found (normal state, not an error).
- **`internal/trust`** — `Allow(path)` / `IsTrusted(path)`. Trust is a SHA-256 hash of the config file's *content*, recorded under `$XDG_DATA_HOME/envoke/allow/<sha256(abs path)>` (or `~/.local/share/...`) — a record file per config path, so distinct configs never collide. `IsTrusted` recomputes the current content hash and compares; any edit — even whitespace — changes the hash and revokes trust until `Allow` runs again. This is the concrete mechanism behind the non-negotiable trust-before-execution principle below; `shell-hook` calls `IsTrusted` before ever calling `executor.Render`.
- **`internal/shellinit`** — `Generate(shell)` returns the literal hook script for `"bash"`, `"zsh"`, `"fish"`, `"tcsh"`, or `"powershell"` (static strings, no templating needed since there's no per-user variation). Every hook calls `envoke shell-hook` with a shell-specific `--shell <name>` flag so `executor.Render` picks the right export dialect. Each hook's mechanism, in increasing order of how many real-interpreter gotchas it cost to get right:
  - **bash** has no native "on cd" hook, so it polls via `PROMPT_COMMAND` (comparing `$PWD` to a var saved after the last prompt) — **the baseline var must be seeded once at hook-install time**, not lazily inside the hook function, or the very first `cd` after installing the hook compares the new directory against itself and gets silently missed (`TestGenerate_BashHookFiresOnFirstCd`, driving real bash/`PROMPT_COMMAND` end to end).
  - **zsh** uses the native `chpwd_functions` array, which only fires on a real `cd` and always has `$OLDPWD` already set by the shell itself, so it needs no seeding trick.
  - **fish** uses the native `--on-variable PWD` event. Fish's own `$OLDPWD` support isn't reliable enough to depend on, so — like bash — the hook tracks and seeds its own baseline var. A bare command substitution in fish splits multi-line output into one list element per line, so `string collect` (fish 3.4+) gathers `envoke shell-hook`'s stdout into one string before `eval`, or a multi-line matched script would silently become several unrelated single-line evals.
  - **tcsh** uses the special `cwdcmd` alias (csh's native "run after every cd/pushd/popd" hook — tcsh maintains `$owd`/`$cwd` itself, no seeding needed), claiming that slot outright rather than chaining with a pre-existing user `cwdcmd` (a documented tcsh idiom, e.g. xterm title-setting) — undocumented limitation, noted in the tcshHook doc comment. Three real bugs found only by driving a real tcsh end to end (string-matching the generated script caught none of them): (1) tcsh has no `export`/`VAR=value` syntax, and both plain and quoted backquote command substitution split multi-line output on newlines, so instead of capturing-then-`eval`, the hook pipes `envoke shell-hook`'s stdout straight into `source /dev/stdin`; (2) `cwdcmd`'s body runs through a restricted internal execution path that does **not** honor `|`/`>` directly — a bare `cmd | source /dev/stdin` inside the alias silently prints to the terminal instead of piping, and a `setenv` inside it never reaches the interactive shell. Wrapping the whole thing in `eval "..."` forces a full re-parse that does honor `|`, and `$owd`/`$cwd` are single-quoted *inside* that eval string (not just around the whole alias) so a directory with a space still reaches `shell-hook` as one argument; (3) tcsh has no `command` builtin — the hook originally used `command envoke ...` (copying the bash/zsh/fish idiom for bypassing a same-named user alias) and this worked on macOS purely by accident, because macOS ships a real `/usr/bin/command` executable; on Linux tcsh it fails outright with "command: Command not found." Fixed to tcsh's own alias-bypass syntax, `\envoke`. `TestGenerate_TcshHookSetenvPersistsInCallingShell` is the regression test for (1)/(2) — note it doesn't just check `envoke` was *called* correctly (a weaker test that already existed passed even with both bugs present, since the call itself succeeded and only the piped/setenv side effect was silently lost). Bug (3) only surfaced once the Dagger CI matrix (step 6, below) ran this suite against Linux's tcsh for the first time.
  - **powershell** wraps the `prompt` function (PowerShell's idiomatic customization point — what posh-git/oh-my-posh also use), saving and always calling through to whatever `prompt` was previously defined, guarded by an installed-flag against double-wrapping if sourced twice. `Out-String` joins `envoke shell-hook`'s output into one string before `Invoke-Expression`, the same multi-line concern as fish's `string collect`.

  None of the five hooks redefine `cd` (regression-tested via `assertNeverRedefinesCd`).
- **`cmd/envoke`** — `version`; `shell-init <bash|zsh|fish|tcsh|powershell>` (prints the hook script); `allow [path]` (defaults to `config.Locate()`, refuses to trust a config that doesn't even parse, then calls `trust.Allow`); `shell-hook [--shell <name>] <from> <to>` (invoked by the installed hook on every `cd` — resolves matches via `matcher.Resolve`, checks `trust.IsTrusted`, and only then prints `executor.Render(shell, ...)`'s output to stdout; an untrusted match is reported on stderr only, with an `envoke allow <path>` hint, and nothing goes to stdout; omitting `--shell`, as bash's/zsh's generated hooks do, defaults to the POSIX profile); `debug <from> <to>` (same `matcher.Resolve` call as shell-hook, but always prints what would fire — plus whether the config is currently trusted — to stdout and never calls `executor.Run`/`executor.Render`, so it's safe to run against an unapproved or half-written config). `run(args, stdout, stderr) int` is the testable dispatcher `main()` wraps.
- **Shell integration**: `envoke shell-init <shell>` prints shell code to `eval`/`source`, hooking the shell's own directory-change mechanism (`chpwd_functions` for zsh, `PROMPT_COMMAND` polling for bash, `--on-variable PWD` for fish, `cwdcmd` for tcsh, a wrapped `prompt` function for PowerShell) — never override `cd` directly.
- **`.dagger/`** — a separate Go module (own `go.mod`, `dagger/envoke`) holding the CI pipeline; not imported by and not a dependency of the main `github.com/Neirda24/envoke` module, so the zero-non-stdlib-dependency rule for the product code is untouched. `main.go` defines checks (Go SDK `// +check` doc-comment pragma, run via `dagger check -m .dagger`): `fmt`/`vet`/`build`/`test` mirror CONTRIBUTING.md's four manual commands exactly; `lint` runs golangci-lint (pinned `v2.12.2`, installed with `GOTOOLCHAIN=auto` since it needs a newer Go than this module's `go.mod` floor); `test-shell-{bash,zsh,fish,tcsh,powershell}` each build a container with exactly one shell installed (zsh/fish/tcsh via `apt-get`, powershell via Microsoft's Debian apt repo, bash already in the base `golang` image) and run `go test ./internal/shellinit/...` in it — a check can't take arguments (Dagger checks are always argument-free), which is why this is five separate check functions sharing a private helper rather than one parameterized check. `dagger.gen.go`/`internal/dagger`/`internal/telemetry` under `.dagger/` are generated-on-demand and gitignored by `dagger init`'s own `.gitignore` — don't hand-edit or commit them; regenerate with `dagger develop -m .dagger` after changing `New`'s signature (needed whenever a constructor-level parameter like `GhAuthToken` is added or changed, since `dagger.gen.go`'s `main()` glue calls `New` positionally). `zizmor`/`actions-up` (`+check`) and `autofix` (plain function, deliberately not a check — see Status) round out `main.go`; `zizmorBase`/`actionsUpBase` are the equivalent of `goBase` for those two tools, both taking the optional `Envoke.GhAuthToken`. `.github/workflows/ci.yml` runs `dagger check -m .dagger` on push/PR to `main` and a daily cron — see Status for what the first real run against this repo's own workflows caught.

## Go conventions

- **CLI framework: stdlib `flag`**, decided at step 1. No subcommands existed yet to justify `cobra`/`urfave-cli`'s added dependency; revisit once step 2 (shell-init) or step 3 (allow) needs real subcommand parsing.
- **Config parser: hand-rolled, not participle.** The grammar is a simple line-oriented format (unindented `enter`/`leave` header, indented dedented body) — a hand-rolled scanner keeps positioned error messages straightforward and avoids a dependency for something this small. Revisit only if the grammar grows real nesting/expressions.
- Table-driven tests via subtests (`Test<Func>_<Scenario>` naming), including regression tests for each ondir bug listed in the README's Design notes table (basename-prefix false positives, `~`/env-var expansion, capture-group exposure, traverse behavior). `go test ./... -race` must pass.
- Static, dependency-free binaries — avoid cgo. Zero non-stdlib imports so far; keep it that way unless a real need appears.
- Generated shell code gets tested with the real interpreter, not just string-matching: `<shell> -n -c <script>` for a syntax check, and for behavioral bugs (like the bash first-cd seeding bug, or tcsh's `cwdcmd`-pipe restriction — both above), drive a real subprocess through `exec.Command` with a stub `envoke` binary on `PATH` and assert on what it was called with *and* that any side effect (a `setenv`/`export`/`set` the stub emits) actually persists in the calling shell — a test that only checks the stub was invoked can pass even when the real bug (a dropped pipe, a forked subshell) is present. `t.Skip` if the interpreter isn't on the test machine's `PATH` — as of this writing fish and PowerShell aren't installed in the dev/CI environment this project has been built in, so their hooks are implemented against documented behavior and covered by syntax/content tests only; their `TestGenerate_*ScriptIsSyntacticallyValid` tests skip rather than run. If you land on a machine with `fish`/`pwsh` available, running those tests for the first time is worth doing before trusting those two hooks as much as bash/zsh/tcsh (all three of which *have* been driven end to end against real interpreters).
- **Trust store location: `$XDG_DATA_HOME` (state), not `$XDG_CONFIG_HOME` (config).** README only specifies XDG support for the config file itself; trust records are runtime state, not config, so they follow the XDG Base Directory Specification's separate data-home convention. Not written in the README — if you change this, update it there too.

## Documentation site

A user-facing docs site (`mkdocs.yml` + `docs/`) is separate from this file and the README — README stays the GitHub-landing pitch, this file stays contributor-facing, and `docs/` is the structured Read the Docs-style site (Getting Started, Configuration, Trust Model, Debugging, Design Notes). Built with MkDocs Material (`docs/requirements.txt` pins the version) rather than Sphinx or Docusaurus — pure Markdown (no rST rewrite) and no Node toolchain in a repo that's otherwise zero-dependency. `docs/contributing.md` embeds the real `CONTRIBUTING.md` verbatim via `pymdownx.snippets` (`--8<-- "CONTRIBUTING.md"`) instead of duplicating it, so there's one source of truth; cross-file links inside `CONTRIBUTING.md` had to become absolute `github.com/Neirda24/envoke/blob/main/...` URLs instead of relative paths, since a relative `CLAUDE.md`/`README.md` link doesn't resolve once the file is rendered under `docs/`'s own path — `mkdocs build --strict` catches this class of broken link, verified locally in a scratch venv before this was committed.

- Preview locally: `pip install -r docs/requirements.txt && mkdocs serve` (live-reload at `localhost:8000`) — or, without installing Python at all, the `Docs` function in `.dagger/main.go`: `dagger -m ./.dagger call docs up --ports 8000:8000` runs the same `mkdocs serve` inside a container and tunnels port 8000 to the host. Its `docsBase()` helper installs `docs/requirements.txt` before the source tree is mounted, so that layer only invalidates on a requirements change, not on every doc edit. The service must be built via `AsService(dagger.ContainerAsServiceOpts{Args: [...]})`, not `WithExec(...).AsService()` — `WithExec` runs the command once during query resolution (its output shows up in build logs, which is misleading) rather than making it the service's persistent entrypoint, so the container never actually listens once `up` tries to tunnel to it.
- `.github/workflows/docs.yml` builds and deploys to GitHub Pages on push to `main` (paths-filtered to `docs/`, `mkdocs.yml`, `CONTRIBUTING.md`) via `actions/deploy-pages` — this is the one GitHub Actions workflow in the repo; it's scoped to docs deployment only and doesn't run the Go checks (that's still `dagger check -m .dagger`, on-demand). Requires the repo's Pages source (Settings → Pages) to be set to "GitHub Actions" once — not something this workflow can do for you.
- `mkdocs-material` announced maintenance mode in early 2026 (feature-frozen since 9.7.0, critical fixes only until Nov 2026) in favor of a future rewrite ("Zensical"). Fine for now given how small this docs site is; worth revisiting the tool choice if that timeline lapses without a stable successor.

## Don't

- Don't add a feature from the README's "Use cases" section before the MVP step it depends on is done.
- Don't add implicit/automatic leave behavior — re-read the "enter/leave are independent" principle above before adding anything that feels like convenience state management.
- Don't let a GitHub Release go out without install/upgrade instructions in its notes. `.goreleaser.yaml`'s `release.footer` template is the mechanism — it's appended after the auto-generated changelog on every release, so this is automatic, not something to add by hand per release. If a new install method ships (Scoop, nfpm, the install script), update the footer template too, not just the README's Installation section.
